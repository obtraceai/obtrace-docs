Source-of-truth setup rules:
- Backend SDKs send OTLP payloads to `/otlp/v1/logs`, `/otlp/v1/traces`, and `/otlp/v1/metrics`.
- Browser SDK also sends replay traffic to `/ingest/replay/chunk` and `/ingest/replay/recipes`.
- Stable runtime identity should include `tenant_id`, `project_id`, `app_id`, `service_name`, `env`, and `service_version`.
- `service_name` maps to OTLP `service.name`.
- `env` maps to OTLP `deployment.environment`.
- `service_version` maps to OTLP `service.version`.
- Region is attached as an event or span attribute when topology matters.

Preferred workflow order:
- Start from `quickstart` for first rollout.
- Use `auth` before language-specific setup if credential scope is unclear.
- Use workflow pages before SDK reference pages when the user asks how to do something end-to-end.
- Use SDK pages when the user needs exact code snippets.
- Use project guides (FastAPI, Spring Boot, NestJS, etc.) when the user names a specific framework.
- Use platform guides when deploying to Vercel, Railway, Fly.io, etc.
- Use integration guides for cloud providers (AWS, GCP, Azure) or container platforms.
- Use security pages when the user asks about repository access, PR permissions, or approval flow.
- Use API reference for request/response shape, auth, or webhook payloads.
- Use MCP docs when the user wants AI assistants to query Obtrace data.
- Use Obtrace Zero docs for zero-instrumentation or eBPF-based observability.
